# PCIe 工程摘要與三層閱讀（UX-01–03）

目的：第一屏直接說明已觀察事實、未確認結果與下一個操作，完整證據保留。
這是現有 Flow 結果的呈現修正，不重排候選、不加入規範違反或根因規則。

| 已確認的介面問題 | 依據 | 影響與修正 |
|---|---|---|
| 原理與內部欄位混在主畫面 | `ShowCandidate` 同時顯示觀察、全範圍 Completion、context 及 action 來源描述 | 嚴重度3；第一屏只留事實、未知、下一步與里程碑含義 |
| 必要條件被當成實際缺口 | `actions.describe` 將每個 required_evidence 標示「仍需證據」 | 嚴重度3；保留完整條件，另產生本次 resolved/missing 清單 |
| 里程碑看似故障推薦 | 主按鈕只有「定位階段證據」 | 嚴重度3；明示核對入口、不是故障位置，按鈕改為查看里程碑 |
| 完成數量的範圍容易誤認 | Completion 計數沒有放在逐階段資料結構內 | 嚴重度3；預設放進進階報告，明示非 L0 後／同裝置配對證據 |
| 下一步缺少具體路徑 | 通用核對 Config/Completion 文字 | 嚴重度3；已綁定後續 Config 可定位，否則顯示明確補資料需求 |

UX-01：`pcie_engineer_view.py` 投影現有階段。有效單方向 L0 是 observed，
不是初始化完成。較後的無效狀態／方向未知／截斷／Flit 不沿用舊 L0。
知識來源不適用不會刪除已有觀察，但不能啟用不受支持的後續建議。

UX-02：第一層白話摘要；第二層事件順序與需補資料；第三層完整來源、
Hash、scope、原始 JSON、知識卡前提與報告。HTML、Markdown 與 WinForms
共用同一投影，原完整報告收合保存，不丟棄。既有 Packet 層與原生定位仍可選。

UX-03：只有同 source/display/namespace、Channel、方向與 observed epoch，
且晚於 L0、有來源的 Config 才可當 follow-up。它是同方向觀察區間的入口，
不代表已證明實體 Link、反向回覆或裝置身分。新增定位仍使用既有 owned-session
路徑與目標 allowlist。沒有有效目標時只要求補資料，不拿舊 Packet 或全範圍
Completion 計數冒充後續證據。

驗證：正反例（含舊 Config、錯來源／方向／epoch、無效 LTSSM、截斷、
空資料、Flit）、摘要／次要定位遭改動拒絕、原規則資料保持一致、WinForms
三層互動與影像檢查、跨協定回歸、最終可攜包離線重播。畫面清楚與否的
5–10秒真人辨識目標仍須真人試用，不用測試通過數代替。
