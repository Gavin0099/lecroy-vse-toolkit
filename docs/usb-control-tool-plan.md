# USB Trace Triage Tool：實作計畫與切片

日期：2026-10-16，審查修訂 r2。依使用者提供的 Plan 審查，保留 TOOL-01～05 的
主要方向，新增 TOOL-02.5 早期人工操作驗證。本輪僅修訂計畫與驗收條件，
**不啟動實作、不修改分析規則、不 commit／push**。以下規格均不是實作完成宣告。

## 要交付的工具

工程師開啟工具，把一份 `.usb` 從 Windows 檔案總管拖入原生入口（也可按鈕選檔），
即開始分析，看到最多三個值得先檢查的區段；每段提供
位置、觀察事實、推薦理由與檢查提示。按「在 LeCroy 定位」後，工具對同一份 trace
的唯讀副本呼叫原生定位 API，工程師核對現場封包。不需要 PASS trace、失敗時間
或先選規則；沒有候選時清楚說明範圍。

第一版範圍：Windows、本機已安裝 LeCroy USB Protocol Suite 10.40 Build 6309、
USB2 標準 EP0 控制傳輸。以最小 VSE 為預設資料路徑；保留既有 Automation adapter
供比較與診斷，不因 VSE 失敗就默默切換成資訊較少的結果。

第一版完成後的完整任務：

1. 雙擊本機啟動器，看到就緒狀態、拖放區與選檔入口。
2. 拖入一份 trace 即開始分析；工具取得真實路徑，建立獨立唯讀副本並執行既有分析。
3. 看到主要候選，或有範圍說明的無候選結果；可展開另外兩個候選與前後證據。
4. 按候選的「在 LeCroy 定位」，開啟／重用該副本並送出 Transfer 定位請求。
5. 在 LeCroy 核對 Transfer、時間、Address／EP，依提示查看封包。
6. 保存本機報告，換一份 trace 或關閉工具；原始檔及使用者原有 LeCroy 工作保留。

驗收以這條任務是否走完為主，不以測試數、JSON 產出或既有資料命中率取代。
不在第一版加入根因自動判定、USB-CV 合規裁決、USB3／PD、雲端上傳、模型服務、
大型 VSE 框架、完整協定 viewer，或依這六份 FAIL 再調排名。

## 最小架構

```text
輕量 Windows 原生入口（拖放／選檔、環境檢查）
    → 本機 Python 控制程式（127.0.0.1、一次一份 trace）
        → 現有 PowerShell runner → 唯讀副本 → 最小 VSE／既有分析
        → 瀏覽器工具頁（讀 inspection.json、候選與操作狀態）
        → PowerShell STA 導航工作程序 → LeCroy COM
              OpenFile(已核實的絕對副本路徑)
              GotoUnit(3,候選的原生 Transfer 編號)
```

建議新增 `tools/start-usb-control-tool.ps1`、`tools/usb_control_app.py`、
`tools/usb-control-navigation.ps1` 與一份工具頁面資源。名稱可在各 slice 實作時微調。
先使用現有 Python／PowerShell；原生入口預設採既有 Windows .NET WinForms，
只負責拖放與選檔，不重寫完整桌面 UI。不先引入 Electron、資料庫或新 Web
framework。瀏覽器只送出這個工作階段的候選選擇，不能直接操作 COM。

原生入口取得檔案路徑後，以結構化 IPC 交給控制程式。瀏覽器不負責接收整份 trace，
也不把 input 的 `C:\fakepath\...` 當實際路徑。保留來源保護所需的一次唯讀副本，
避免另加瀏覽器上傳或 base64 搬運。這個選擇依據 [MDN 檔案輸入說明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file)
及 [WinForms 原生拖放說明](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/advanced/walkthrough-performing-a-drag-and-drop-operation-in-windows-forms)；
本機拖放與 IPC 整合仍須在 TOOL-02 實作驗證。

控制程式負責工作狀態與報告，導航工作程序串行持有 COM 物件；不從多個 HTTP
執行緒同時操作 COM。擷取完成並釋放其原生程序後，導航工作程序才開啟同一副本，
避免現有 runner 的「已存在 UsbSuite 就拒絕執行」條件與新導航功能互相衝突。
現有 guard 先保留；只有 TOOL-01 證明可安全區分自有實例後，才在 TOOL-02 有界
調整擷取／導航協調。沒有多實例證據時不能直接移除 guard。

### LeCroy 共存與程序所有權（TOOL-01 先驗證）

先用受控的兩個測試工作階段模擬「工程師已開著 LeCroy」，不拿使用者目前未保存
的工作當探索樣本。分別驗證 COM 啟動會新建實例、共用程序但有可區分的文件／物件，
或直接重用同一工作階段；**多實例能力目前未知**。

- 在對目標呼叫 OpenFile／GotoUnit／Close 前，必須已核實目標由工具擁有且隔離。
  單看 `New-Object` 成功、程序名稱或新增 PID 不足以證明 COM 綁定到哪個工作階段。
- 記錄前後 PID／視窗／開啟文件身分及綁定依據；測試既有工作階段的 trace、位置與
  未保存狀態是否保持不變。涵蓋擷取、定位與關閉，不只測單一 GotoUnit。
- 若能安全共存，才允許工具操作自有實例；若不支援或所有權不明，維持可見衝突狀態，
  不接管、不關閉、不切換或終止使用者的 LeCroy，也不自動嘗試「恢復」其工作。
- 共存限制要列入 TOOL-02.5／05 的操作成本與未完成原因；不能把要求工程師關閉
  LeCroy 的時間排除後再宣稱省時。

### COM STA 訊息處理、序列化與失聯

COM 物件在同一個 STA 建立、呼叫及釋放；該 STA 必須有持續運作的 message pump，
不能只加 `-STA` 就視為完成。[Microsoft STA 說明](https://learn.microsoft.com/en-us/windows/win32/com/single-threaded-apartments)
也指出訊息迴圈與重入的限制；採用 STA 本身不保證不會卡住。

- 候選請求由 IPC 接收端送到 STA 佇列；讀取 IPC 的阻塞等待不放在 STA 訊息迴圈。
  一次只執行一個 COM 操作，以 busy 狀態防止 message pump 引發重入及交錯開檔。
- 原生入口、HTTP 狀態服務與 COM worker 分離；耗時呼叫不能阻塞整個工具頁／入口。
  controller 的監看與 deadline 在 worker 外運作，不能靠卡住的 STA 自報超時。
- TOOL-01 實作前設定並記錄呼叫 deadline／失聯條件。逾時顯示「無回應，定位結果未知」，
  不把 HTTP 接收、API 返回、GUI 落點確認混為一個成功狀態。
- 逾時不代表 COM 已取消。禁止盲目重送、換檔或把遲到回覆套到新工作階段；確認
  舊 worker／自有原生工作已結束並核對副本後，才開放重試。
- 異常清理先嘗試釋放自有 trace／COM。若需終止失聯 worker 或自有原生程序，必須
  已能證明專屬所有權且不承載使用者工作；所有權不明時不終止，保留衝突與診斷。

這些是待驗證設計，尚未證明長駐 worker、多實例、取消或瀏覽器橋接可用。

定位請求使用本機工作階段 ID 與候選 ID，伺服端從已載入的模型取原生 Transfer；
頁面不能傳任意路徑、程式或 COM 方法。本機服務的驗收要求為：

- 只綁 `127.0.0.1`，啟動時由 OS 配發一個可用埠並保持該 socket，不掃描埠範圍或
  暴露 LAN；本次服務只接受實際綁定的 `Host: 127.0.0.1:<port>`。
- 定位只接受 POST、限定 JSON 格式與大小；精確比對本次 `Origin` 的 scheme／host／port，
  拒絕不符、缺少或 `null` 的 Origin，不開放跨來源 CORS 控制。GET 不觸發 COM 動作。
- 使用每次啟動重新產生的不可預測工作階段 token；請求須同時通過 token、目前工作
  階段、合法候選與 trace hash 綁定，重啟後舊 token／候選失效。不將 token 寫入報告、
  可分享 URL 或持久日誌。來源檢查不能取代工作階段授權。
- HTTP 僅提供本次工具頁／報告的允許資源，不把 repo 或輸入目錄作為可瀏覽檔案根。
  原生選檔路徑只經受控 IPC；不接受網頁指定任意本機檔案。
- 啟動 worker 使用固定程式／腳本與參數陣列或結構化 IPC；不用字串拼接 PowerShell
  指令、`Invoke-Expression` 或 shell 展開。空白、Unicode、引號、反引號、`$()` 與
  分號等路徑內容只能當資料，必須有拒絕／正確傳遞的測試。

來源驗證原則參考 [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。
上述精確 Host／Origin／token 政策是本工具規格；沒有因此宣稱已完成安全實作或稽核。

輸出維持現有 inspection.json 的證據邊界；原始事件／模型與工具執行狀態分開保存。
UI 顯示來源 basename、短 hash、後端、規則版與觀測範圍，這些顯示資訊不進排序。
第一版首屏維持 Top 3；總數與省略數直接顯示，例如「找到 4 段，顯示前三，另 1 段
未顯示」。展開其餘候選留待個別需求，不為了列表改動 discover 或擴大模型。
TOOL-02 給工程師試用前就須有這項最低揭露，不延後到 TOOL-03 才修正誤讀風險。
同時常駐顯示「USB2 標準 EP0 控制傳輸檢查；未涵蓋 USB3 Link、Bulk、Interrupt、
PD 及其他協定問題」。無候選不等於整份 trace 或 USB PASS。

## 必須處理的操作狀態

| 狀態／情境 | 使用者看到的行為 |
| --- | --- |
| 待匯入／就緒 | 拖入或選一份 trace；看得到 LeCroy 與執行環境是否可用 |
| 建立副本／讀取／擷取／分析 | 顯示實際階段與已經過時間；未知進度不捏造百分比 |
| 有候選 | 一個主要候選、最多兩個次要候選；每卡都有定位按鈕 |
| 無候選／部分資料 | 清楚說明分析範圍與缺口；不顯示整體 PASS |
| 正在定位 | 暫時停用重複操作，顯示目標 trace／Transfer |
| 定位 API 返回 | 顯示「定位請求已送至 LeCroy，請核對 Transfer 與時間」；不假裝已自動讀回 GUI |
| 無法切到前景 | 保留定位結果並提示切換 LeCroy；不得聲稱視窗已顯示 |
| LeCroy 已被使用者開啟 | 僅在已證明隔離時使用自有實例；否則顯示衝突，不動其 trace／程序 |
| COM 無回應／遲到回覆 | 入口與狀態頁仍可回應；顯示結果未知，清理確認前不重送／換檔 |
| 換 trace | 先完成／中止本工具的工作並釋放擁有的原生物件，再開始下一份 |
| 工作失敗／使用者關閉 | 保留診斷，確認自有程序清理結果；清理未確認時不顯示就緒或允許下一次擷取 |

取消的細節在 TOOL-02 實作前定義：選檔取消不建立工作；原生呼叫中若沒有已驗證
的安全取消介面，就先阻止換檔並顯示等待／清理狀態，不承諾立即取消，不終止
使用者的 LeCroy 程序。UI 的關閉要求與實際原生清理完成須分開處理。

### TOOL-01：先把「在 LeCroy 定位」接通

**交付**：以已保存的報告為輸入，從本機服務開啟工具頁，按候選按鈕即可針對已核實
副本呼叫 GotoUnit。先走通 FAIL_01 與 FAIL_06，不重新分析、不修改排序。CLI／COM
再次成功不算這片完成，必須真的從瀏覽器按鈕走到原生畫面。

**實作範圍**：最小 loopback controller、單一 COM 導航 worker、候選按鈕、狀態回饋；
復用 model 裡的時間、Transfer 及 trace hash。每次定位前核對副本與工作階段綁定。
先完成上列共存／所有權調查、STA 訊息處理與序列化設計、失聯恢復及本機請求限制。
只有已證明隔離才操作自有實例；若未能證明，保留衝突限制與工程師成本紀錄。

**驗收**：

- 從頁面點選 1386、562、372、446，原生畫面的編號、時間與 Address/EP 對得上。
- 包含至少一次不同候選間切換；重複點擊不造成多個開檔／交錯定位。
- 測試無既有 LeCroy、受控既有工作階段、自有導航已開啟三種情境；保留 COM 綁定
  依據與前後原生畫面／文件狀態。共存失敗可以保留限制，但不能聲稱共存通過。
- 以失聯／卡住的 worker 進行故障注入，確認原生入口與狀態頁仍可回應；另測真實
  LeCroy COM 異常與退出，不用 mock 成功取代 native 正常定位證據。
- 驗證連續切換、同時／重複請求、重入、超時後遲到回覆、關閉與重新開啟；確認
  一次一個 COM 操作，未完成清理不開新工作，且不影響既有使用者工作階段。
- 錯誤 hash、過期 token／工作階段、越界候選、不符 Host／Origin、跨來源／無 token
  請求、錯誤方法及路徑／命令注入字串均遭拒；斷言未呼叫 COM，不只斷言錯誤碼。
- 分開保存 HTTP 已接收、API 已返回、人工核對 GUI 的證據；逾時或畫面未確認不可
  顯示「GUI 已正確定位」。COM 失敗與共存衝突有可見訊息。
- 從瀏覽器點擊後測試視窗前景行為；若 Windows 限制切換，提供可見手動切換提示。
- 原始 trace／唯讀副本檢查通過，關閉後本工具擁有的原生程序退出。

**可審查邊界**：只接一個必要動作，不建立泛用 COM 控制 API；不改現有規則與模型。

### TOOL-02：單一 trace 的完整工具流程

**交付**：雙擊啟動器 → 從檔案總管拖入單一 trace（或原生選檔）→ 自動跑預設 VSE →
工具頁顯示結果 →
使用 TOOL-01 定位。工程師不必開終端機、組路徑或找 index.html。支援有候選與
無候選結果，且可結束本次工作後再選下一份。

**實作範圍**：輕量 WinForms FileDrop／選檔入口、真實路徑 IPC、環境檢查、每次新
工作目錄、背景 runner、可見階段、結果載入。只傳路徑與狀態，不經瀏覽器上傳整檔。
處理擷取與導航 worker 的先後關係；沿用現有完整性檢查。原生呼叫中取消／關閉的
可達行為需先寫入測試情境，再實作，不預設有安全的即時取消 API。

**驗收**：

- 由實際 Windows 檔案總管拖入 FAIL_01，走完分析、報告、一鍵定位；另驗證選檔
  路線及 PASS_04 無候選，不需事前失敗時間或 PASS 檔。不用直接餵路徑的測試取代拖放。
- 拖放多檔／資料夾／非 .usb、無法讀取／已移走的檔案、忙碌中再次拖入、選檔取消
  均有明確處理；首版一次只接受一份，不靜默挑第一檔。不要求以管理員權限執行。
- Unicode／空白／特殊字元路徑、缺 Python／LeCroy／原生入口相依元件、擷取失敗、資料截斷、
  原始檔變動、既有輸出目錄均不誤顯分析成功。
- 兩次連續不同 trace 工作不殘留上一份的候選與定位綁定；不覆寫歷史結果。
- 測試執行中關閉／再次開啟與清理失敗，確認不誤殺或接管使用者程序。
- 核對工具載入的模型與凍結 CLI 對同一來源的輸出一致，標籤只供顯示。
- 首屏顯示候選總數／未展示數與 USB2 EP0 範圍，FAIL_06 不得讓前三看似全部；
  用未含可分析 USB2 EP0 的輸入核對無候選提示，不宣告 USB3／PD 正常。
- 記錄原生路徑、必要副本次數與磁碟量，確認沒有額外瀏覽器整檔上傳／base64 副本。

### TOOL-02.5：及早讓工程師實際走完整流程

**交付**：TOOL-02 完成後，先讓 1～2 位工程師使用既有案例，包括單一候選、多候選
與無候選情境。目標是找操作摩擦，不等 TOOL-04／05 才第一次由工程師操作。

**驗收**：觀察拖放入口是否找得到、能否說出主要線索與證據缺口、是否注意未顯示
候選及範圍限制、能否一鍵定位並核對原生欄位。另走一次可恢復錯誤／既有 LeCroy
衝突路徑；記錄步驟、遲疑／求助、錯誤操作、定位與共存成本、任務完成與初步耗時。
記錄工程師對案例的既有熟悉程度，不能把熟悉案例的時間當成陌生 trace 省時證明。

產出可重現的問題、影響與 TOOL-03 待修項目；沒有工程師參與時維持「待人工驗證」，
不得用開發者自測、瀏覽器檢查或文件簽名取代。待參與期間可整理已知問題，不能
自行宣稱依使用者觀察完成 TOOL-03。此項不取代 TOOL-05 盲測。

### TOOL-03：讓工程師不用猜操作與涵蓋範圍

**交付**：以 TOOL-02.5 觀察的停頓、誤讀、求助與操作失敗決定修正優先序；
補齊首屏 trace 身分、後端／規則版本、候選總數／省略數、明確的定位
動作、回到檔案選擇及證據細節。保留一張主要卡；FAIL_06 預設另兩張收合，但清楚
說明共四段只顯示前三。USB2 EP0 範圍及未涵蓋 USB3 Link、Bulk、Interrupt、PD
的揭露不可被優化移入難以發現的位置；UI 的缺資料／錯誤／無候選用詞一致。

**驗收**：FAIL_01、FAIL_06、PASS_04 的實際畫面；鍵盤可啟動定位與展開內容，
重複點擊／重試／換檔狀態正確；桌面與 390px 無阻擋核心動作的溢出。依
`usb-control-product-validation.md` 與 TOOL-02.5 的具體問題逐項覆核，保留原問題與
修正後結果；必要時請原工程師重走受影響步驟。泛化與省時結論仍留待 TOOL-05。
不以這一片提高 Top 3 命中率，也不把 UI 審查分數當產品效益。

### TOOL-04：可交給工程師試用的本機版本

**交付**：一份工具 ZIP，含雙擊入口、必要來源／頁面資源、短版操作說明、版本資訊
及範例報告；不內含 LeCroy 安裝包、授權或專有原始 capture。首版使用現有可驗證的
Python／PowerShell runtime；免 Python 安裝的獨立 EXE 不列為本片承諾。

**驗收**：在新解壓目錄、不依賴 repo cwd 或開發機絕對路徑啟動；另在乾淨 Windows
環境驗證實際相依。逐一缺少 Python、PowerShell／.NET 入口相依、LeCroy 或 COM
註冊時，訊息能指出缺件與處理方式，不顯示空白頁／假成功，也不自動安裝或提權。
若未取得乾淨環境，必須分開報告「新目錄通過、乾淨環境未驗」，不能合併稱通過。

以實際 trace 跑一次有候選、一次無候選及一次定位；另挑至少一份具代表性的較大
trace，記錄檔案大小、callbacks／控制傳輸量、截斷情形、機器／軟體版本、各階段
及總耗時、工具與自有 LeCroy 程序的個別峰值記憶體、工作目錄峰值磁碟用量與清理
後保留量；共用程序無法歸因時明示量測限制，不把不同時點的峰值相加當同時總量。
同時核對 UI／狀態服務可回應、空間不足與失聯恢復；只有開發機單次量測時不宣稱
通用效能。大型 trace 未取得則保留待測，不用小檔測試代替。

保留安裝版本、工具 hash 與來源保護檢查，封存此版供 TOOL-05 使用。沒有實測
依據前不編造效能／資源達標門檻；TOOL-02.5 發現的可接受等待需求可作後續門檻來源。

### TOOL-05：驗收陌生案例與省時價值

**交付**：由未參與案例開發的工程師，用未拿來調規則的 FAIL/PASS 完成「理解提示、
定位、核對證據」任務；事前約定何謂正確／有用，不由程式根據檔名宣判結果。

**驗收**：先封存程式與資料 hash，搜尋後才揭露標註；記錄有效候選命中、錯誤導引、
漏失、求助與未完成。前三標註覆蓋、有用但未標註的線索、以及實際帶錯方向的候選

判定者，不能把「未命中註記」直接算錯誤。時間包含拖放匯入、來源副本、載入、
